第 8 章 · Part 3：E2E 測試

Vitest + OpenCLI 測試架構

OpenCLI 是一支 CLI 工具，本身沒有內建 test runner。本章帶你從零搭建一套以 Vitest 為核心的 E2E 測試架構， 涵蓋目錄結構、所有配置檔案、跨平台 spawn 包裝，以及 Windows 環境下三個容易踩到的坑。

為什麼選 Vitest 搭配 OpenCLI

OpenCLI 透過 child_process.spawn 呼叫，任何能執行 Node.js 的 test runner 都可以搭配。 選擇 Vitest 的理由：

  • 輕量、零設定 TypeScript：內建 ts-node/esbuild，不需要額外的 Babel 或 ts-jest 設定
  • 原生支援 ESM：OpenCLI helper 以 ESM 撰寫，Vitest 不需要任何轉換設定
  • 彈性 timeout：E2E 測試需要遠比 unit test 更長的等待時間，Vitest 支援 per-suite 細調
  • JUnit reporter 內建：CI 環境（GitHub Actions、GitLab CI）可直接讀取測試報告

整體架構如下：

整體呼叫鏈 
Vitest spec
  └── describe / it / expect        ← 測試邏輯 + 斷言
        └── helpers/opencli.ts      ← spawn 包裝
              └── child_process.spawn('opencli', [...args])
                    └── OpenCLI daemon
                          └── Chrome（CDP）
💡
daemon 模式

OpenCLI daemon 在第一次呼叫時自動啟動，後續指令複用同一個 Chrome session。 測試完畢後 daemon 會繼續存活，方便手動除錯。若要強制重啟，執行 opencli browser <session> close。

目錄結構

建議將 E2E 測試放在專案根目錄的 e2e/ 子目錄，與主應用程式的 package.json 完全隔離， 避免開發依賴污染正式 bundle。

e2e/ 目錄結構 
project-root/e2e/
├── package.json
├── tsconfig.json
├── vitest.config.ts
├── .env.example
├── .gitignore
├── helpers/
│   ├── opencli.ts            # spawn 包裝（跨平台）
│   └── chat.ts               # 業務專屬 helper（針對目標站）
├── specs/
│   ├── 01-smoke.spec.ts      # 冒煙測試
│   └── 02-flow.spec.ts       # 完整流程測試
└── artifacts/                # 截圖、JUnit 報告（gitignored）
  • helpers/opencli.ts：唯一知道如何呼叫 opencli CLI 的模組，所有 spec 透過它操作瀏覽器
  • helpers/chat.ts（選用）：封裝業務邏輯，例如「登入」「送出一則訊息」等高階動作
  • specs/：純測試邏輯，只使用 helper 函數，不直接呼叫 spawn
  • artifacts/：執行期產生，全部 gitignore，CI 透過 upload-artifact 保存

配置檔案逐一說明

package.json

最小依賴集：只需要 vitest、typescript、tsx（Vitest 內部用）以及 @types/node。 不需要安裝 Playwright、Puppeteer 或任何瀏覽器 driver——OpenCLI 負責所有 Chrome 通訊。

e2e/package.json 
{
  "name": "my-e2e",
  "private": true,
  "type": "module",
  "scripts": {
    "e2e": "vitest run",
    "e2e:watch": "vitest"
  },
  "devDependencies": {
    "@types/node": "^22.10.0",
    "tsx": "^4.19.2",
    "typescript": "^5.7.2",
    "vitest": "^2.1.8"
  }
}

vitest.config.ts

以下是針對 E2E 場景調整的完整設定，每個關鍵項目都有說明：

e2e/vitest.config.ts 
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    globals: true,
    include: ['specs/**/*.spec.ts'],
    testTimeout: 120_000,       // 2 分鐘：E2E 操作遠比 unit test 慢
    hookTimeout: 60_000,        // beforeAll/afterAll 也需要寬鬆的超時
    reporters: ['default', 'junit'],
    outputFile: { junit: 'artifacts/junit.xml' },
    pool: 'forks',
    poolOptions: {
      forks: { singleFork: true },   // ⚠️ 關鍵：避免 session 衝突
    },
  },
});
為什麼 singleFork: true 是關鍵設定？
Vitest 預設使用多個 worker process 並行跑測試以提升速度。但 OpenCLI session 是以名稱識別的全域資源： 如果 01-smoke.spec.ts 和 02-flow.spec.ts 同時跑，兩個 worker 都會對同一個 e2e session 下指令，造成點擊錯位、截圖混亂等難以重現的失敗。 singleFork: true 強制所有 spec 在同一個 process 中依序執行，犧牲少量速度換取穩定性。

helpers/opencli.ts（完整 spawn 包裝）

這是整個架構的核心模組。它封裝了三件事：跨平台引號處理、session 名稱注入、以及統一的錯誤拋出。

e2e/helpers/opencli.ts 
import { spawn } from 'node:child_process';

/**
 * shell:true 在 Windows 不會自動 quote 含空白的 args（Node DEP0190）。
 * 此函數確保任何含有特殊字元的 arg 都被正確加上引號。
 */
function quoteForShell(a: string): string {
  if (a === '' || /[\s"'`$&|<>(){};,?*^!%]/.test(a)) {
    return '"' + a.replace(/(["\\])/g, '\\$1') + '"';
  }
  return a;
}

const SESSION = process.env.OPENCLI_SESSION ?? 'e2e';

export async function runCli(args: string[]) {
  const quoted = args.map(quoteForShell);
  return new Promise<{ code: number; stdout: string; stderr: string }>((res) => {
    const p = spawn('opencli', quoted, {
      shell: true,
      env: { ...process.env, NODE_OPTIONS: '--use-system-ca' },
    });
    let stdout = '', stderr = '';
    p.stdout.on('data', d => stdout += d);
    p.stderr.on('data', d => stderr += d);
    p.on('close', code => res({ code: code ?? -1, stdout, stderr }));
  });
}

export const browser = (...a: string[]) => runCli(['browser', SESSION, ...a]);

export async function open(url: string)          { return must(await browser('open', url)); }
export async function state()                    { return must(await browser('state')).stdout; }
export async function click(t: string)           { return must(await browser('click', t)); }
export async function fill(t: string, x: string) { return must(await browser('fill', t, x)); }
export async function keys(k: string)            { return must(await browser('keys', k)); }
export async function screenshot(p: string)      { return must(await browser('screenshot', `artifacts/${p}`)); }

export async function evalJs(js: string) {
  const r = must(await browser('eval', js));
  try { return JSON.parse(r.stdout); } catch { return r.stdout.trim(); }
}

function must(r: { code: number; stdout: string; stderr: string }) {
  if (r.code !== 0) throw new Error(r.stderr || r.stdout);
  return r;
}
💡
NODE_OPTIONS: '--use-system-ca'

在公司 proxy 或自簽憑證環境下，Node.js 18+ 預設不信任系統憑證庫。 加上這個環境變數可讓 OpenCLI daemon 的 HTTPS 請求正常通過 proxy，避免 CERT_UNTRUSTED 錯誤。

加上這一行，TypeScript 才能認識 describe、it、expect 等全域函數， 不需要在每個 spec 檔案頂端 import。對應 vitest.config.ts 裡的 globals: true。

⚠️ Windows + Vitest 環境三大坑

在 Windows 環境下整合 Vitest 與 OpenCLI，有三個坑幾乎每個人都會踩到。 以下逐一說明症狀、原因與解法。

🚫
坑 1：BASE_URL 環境變數被 Vitest 蓋成 /

症狀：在 PowerShell 設好 $env:BASE_URL="http://localhost:8090"， 但 spec 裡讀到的卻是 /，導致所有 open() 呼叫都失敗。

原因：Vitest 繼承 Vite 的環境變數機制，啟動時會強制把 process.env.BASE_URL 設成 /（Vite 的 public base path）。 同樣受影響的還有 MODE、PROD、DEV、SSR、NODE_ENV。

解法：改用任何其他名稱，例如 APP_URL、PORTAL_URL、 E2E_BASE_URL。只要不叫 BASE_URL 就安全。

🚫
坑 2：spawn(cmd, args, {shell:true}) 在 Windows 不自動 quote 參數

症狀：填入含空白的文字（例如 'Alarm Code 有幾種'）， CLI 收到的不是一個 arg，而是被空白切成多個 token，造成指令解析失敗。 Node.js 也會印出 DEP0190 棄用警告。

原因：在 Unix 上，shell:true 使用 /bin/sh -c， args 陣列會被正確合併；在 Windows 上使用 cmd.exe /c，含空白的 arg 必須手動加引號才能被正確解析。

解法：使用上方 opencli.ts 中的 quoteForShell() 函數， 在傳入 spawn 前先將所有含特殊字元的 arg 包上雙引號。

🚫
坑 3：opencli browser eval 不接受多行 JavaScript

症狀：把多行 JS（含換行）傳給 eval 指令，CLI 回傳語法錯誤或只執行第一行。

原因：OpenCLI 透過 shell 傳遞 eval 參數，換行字元在 shell 層被截斷。

解法：所有 eval 邏輯寫成單行。善用 Array.from()、 三元運算子、逗號運算子等技巧取代 IIFE 或多行語句。例如： 

// ✅ 正確：單行
await evalJs('Array.from(document.querySelectorAll("h2")).map(e => e.textContent)');

// ❌ 錯誤：多行（含換行）
await evalJs(\`
  const items = document.querySelectorAll("h2");
  return Array.from(items).map(e => e.textContent);
\`);

執行測試

確認 OpenCLI daemon 已啟動（或讓第一個 open() 呼叫自動觸發啟動），然後：

本機執行 
cd e2e
npm install

# 設定環境變數（注意：不要用 BASE_URL）
$env:APP_URL = "http://localhost:8090"
$env:OPENCLI_SESSION = "e2e"

# 執行所有測試
npm run e2e

# Watch 模式（開發時即時重跑）
npm run e2e:watch

# 只跑特定 spec（除錯用）
npx vitest run specs/01-smoke.spec.ts

測試完成後，JUnit 報告會寫到 artifacts/junit.xml， 截圖則依 spec 中 screenshot() 的呼叫存到 artifacts/ 目錄。

CI 環境設定（GitHub Actions）

在 CI 環境中，瀏覽器通常以 headless 模式由 CDP endpoint 提供，需額外設定 OPENCLI_CDP_ENDPOINT：

GitHub Actions 片段 
- name: Install OpenCLI
  run: npm install -g @jackwener/opencli

- name: Install E2E dependencies
  run: cd e2e && npm install

- name: Run E2E tests
  run: cd e2e && npm run e2e
  env:
    OPENCLI_CDP_ENDPOINT: ws://localhost:3000
    APP_URL: http://localhost:8090

- name: Upload artifacts
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: e2e-artifacts
    path: e2e/artifacts/
💡
if: always()

即使測試失敗，也要上傳 artifacts。失敗時的截圖和 JUnit XML 是除錯最重要的依據， 務必設成 always() 而非預設的「只在成功時執行」。
