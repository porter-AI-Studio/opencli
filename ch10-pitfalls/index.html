第 10 章 · Part 3：E2E 測試

三大陷阱與 Debug 技巧

E2E 測試最讓人抓狂的不是「寫不出來」，而是「偶爾失敗」——本機通過、CI 卻掛掉； 單獨跑正常、合在一起跑就炸。本章整理三個最高頻的陷阱，搭配三套 Debug 技巧， 讓你在 10 分鐘內定位 9 成的 flaky test 問題。

陷阱一：Session 污染

什麼是 Session 污染

OpenCLI 的 session 是以名稱識別的全域資源。當你在 vitest.config.ts 設定 singleFork: true，所有 spec 依序跑在同一個 process 中，但它們共用同一個 Chrome session——上一支 spec 留下的狀態（登入狀態、填了一半的表單、URL）會直接影響下一支。

典型症狀
  • 單獨跑 npx vitest run specs/02-search.spec.ts 完全正常
  • 合併跑 npm run e2e（所有 spec）時失敗
  • 失敗的截圖顯示頁面不是測試預期的起始狀態（例如已經登入、或停在前一個測試的 URL）

根本原因

singleFork: true 讓所有 spec 在同一個 process 中依序執行，避免多個 worker 搶同一個 session。 但這樣一來，session 的瀏覽器狀態（cookie、localStorage、當前 URL）在 spec 之間是共用的。 如果前一個 spec 結束時沒有清理，後一個 spec 就會繼承這些「殘留狀態」。

❌ 錯誤：沒有清理 session 狀態 
// ❌ 錯誤：兩支 spec 都使用同一個 session "e2e"
// specs/01-login.spec.ts
describe('登入流程', () => {
  beforeAll(async () => {
    await open('http://localhost:8090/login');
    await fill('#email', 'user@test.com');
    await fill('#password', 'secret');
    await click('button[type="submit"]');
  });
  // ... 測試通過 ✅

  // ⚠️ 測試結束後 session 仍保持登入狀態
  // 沒有 afterAll 呼叫 session close 或清除 cookie
});

// specs/02-search.spec.ts（接著跑）
describe('搜尋功能', () => {
  beforeAll(async () => {
    // 本以為是乾淨的 session，其實繼承了上面的登入狀態！
    await open('http://localhost:8090/search');
    // 可能看到登入後才有的 UI，導致斷言失敗
  });
});

解法一：afterAll 確保 session close

最簡單的修法：每個 describe 的 afterAll 都關閉 session。 下一個 spec 的第一次 open() 會自動開啟一個全新的 session。

✅ 解法一：afterAll 關閉 session 
// ✅ 解法一：afterAll 確保關閉 session
import { browser } from '../helpers/opencli';

describe('登入流程', () => {
  afterAll(async () => {
    // 無論成功失敗，都關閉 session 釋放狀態
    await browser('session', 'close');
  });

  it('能成功登入', async () => {
    await open('http://localhost:8090/login');
    // ...
  });
});

解法二：每個 Suite 用不同 Session 名稱

更徹底的隔離：不同 spec 使用不同的 session 名稱（e2e-login、e2e-search）， 對應到 Chrome 的不同分頁群組，狀態完全不互通。

✅ 解法二：不同 suite 用不同 session 名稱 
// ✅ 解法二：每個 suite 用不同 session 名稱
// helpers/opencli.ts 支援透過環境變數或直接指定 session

// specs/01-login.spec.ts
const SESSION = 'e2e-login';
const browser = (...a: string[]) => runCli(['browser', SESSION, ...a]);

// specs/02-search.spec.ts
const SESSION = 'e2e-search';
const browser = (...a: string[]) => runCli(['browser', SESSION, ...a]);

// 兩個 suite 的 Chrome session 完全隔離，不會互相干擾
何時用哪種解法？

若 spec 數量少（< 5 支）且 Chrome 效能充裕，推薦解法二：完全隔離，零風險。 若追求少開 Chrome 實例，用解法一：確保 afterAll 確實關閉，再搭配解法三按需清除 cookie。

解法三：beforeAll 開新分頁並清除 Cookie

當必須複用同一個 session 時，在每個 suite 的 beforeAll 用 JavaScript 清除所有瀏覽器狀態。

✅ 解法三：beforeAll 清除 cookie 和 storage 
// ✅ 解法三：beforeAll 開新分頁並清除 cookie
describe('搜尋功能', () => {
  beforeAll(async () => {
    // 方法 A：用 eval 清除所有 cookie 和 localStorage
    await evalJs('document.cookie.split(";").forEach(c => { document.cookie = c.replace(/^ +/, "").replace(/=.*/, "=;expires=" + new Date().toUTCString() + ";path=/"); })');
    await evalJs('localStorage.clear(); sessionStorage.clear()');

    // 方法 B：開啟一個全新的私密分頁（如果 OpenCLI 版本支援）
    await browser('tab', 'new');

    // 方法 C：直接導向登出頁面確保清除狀態
    await open('http://localhost:8090/logout');
    await open('http://localhost:8090/search');
  });
});

陷阱二：時序競爭（Race Condition）

症狀

測試「偶爾」失敗——有時通過、有時掛掉，而且每次失敗的位置可能不一樣。 截圖顯示頁面還在顯示 loading spinner，或 API 回應尚未到達。 在本機跑快的時候通過，CI 機器比較慢時就失敗。

典型症狀
  • Vitest 報告 AssertionError: expected '...' to contain '載入完成'，但手動查看瀏覽器時頁面是正常的
  • 在 --reporter=verbose 下看到某個測試在接近 timeout 時才失敗
  • 截圖顯示 spinner 或骨架屏（skeleton），表示頁面還在載入

根本原因

cli.click() 只是「發送點擊事件」，不等待後續的 DOM 更新或 API 回應完成。 如果立即呼叫 cli.state()，此時頁面可能還在：

  • 等待 API 回應（fetch / XHR in flight）
  • React / Vue 重新渲染（diff 尚未提交到 DOM）
  • CSS transition 播放中（元素存在但不可見）
  • Router 切換頁面（新頁面尚未掛載）
❌ 錯誤：click 後立即 assert 
// ❌ 錯誤：click 後立即 assert，頁面可能還沒更新
it('點擊送出後顯示成功訊息', async () => {
  await click('button[type="submit"]');

  // 💥 此時頁面可能還在處理請求，DOM 尚未更新
  const dom = await state();
  expect(dom).toContain('送出成功');  // 偶爾失敗！
});
✅ 正確：click → wait → assert 
// ✅ 正確：click → wait selector → assert
it('點擊送出後顯示成功訊息', async () => {
  await click('button[type="submit"]');

  // 先等待成功訊息元素出現，再讀取狀態
  await browser('wait', 'selector', '.success-message', '--timeout', '10000');

  const dom = await state();
  expect(dom).toContain('送出成功');  // 穩定通過 ✅
});

非同步 Loading 的多種等待策略

根據頁面行為選擇對應的 wait 指令：

三種 wait 策略 
// 等待頁面出現特定文字（適合沒有固定 selector 的情況）
await browser('wait', 'text', '載入完成', '--timeout', '15000');

// 等待 XHR / fetch 請求完成（適合 SPA 路由切換後）
await browser('wait', 'xhr', '/api/search', '--timeout', '10000');

// 等待元素消失（例如 loading spinner 消失）
// 技巧：先 wait selector 確認 spinner 存在，再 poll until gone
await browser('wait', 'selector', '.spinner:not([style*="display: none"])', '--timeout', '5000');
選擇 wait 策略的原則
  • wait selector：有明確的 CSS selector，這是最穩定的選擇
  • wait text：沒有固定 class/id，但知道頁面會出現某段文字
  • wait xhr：需要等待特定 API 請求完成（適合 SPA 路由切換）
  • 都不確定？先用 state --source dom 看 HTML，再決定 wait 條件

Streaming API 的特殊處理

Streaming chatbot 的回覆是逐字串流輸出，沒有固定的「完成」事件可以 wait。 第 7 章介紹的 waitReplyComplete 模式用「文字長度穩定 4 秒」來判斷回覆完成：

Streaming API 等待完成（waitReplyComplete 模式） 
/**
 * Streaming API 的特殊處理：等待 chatbot 回覆完成
 * 策略：bot 訊息數量增加後，頁面文字長度連續 4 秒不再變化，視為回覆完成。
 * （完整實作參考第 7 章 waitReplyComplete 模式）
 */
async function waitReplyComplete(startCount: number, timeoutMs = 90_000): Promise<string> {
  const t0 = Date.now();
  let lastLen = -1;
  let stableSince = Date.now();
  let seen = false;

  while (Date.now() - t0 < timeoutMs) {
    const count = Number(await evalJs(
      `document.querySelectorAll('.message.bot').length`
    ));
    if (count > startCount) seen = true;

    const text = String(await evalJs(`document.body.innerText`));

    if (text.length === lastLen && seen && Date.now() - stableSince >= 4000) {
      return text;  // 穩定超過 4 秒，視為完成
    }
    if (text.length !== lastLen) {
      lastLen = text.length;
      stableSince = Date.now();
    }
    await new Promise(r => setTimeout(r, 1000));
  }
  throw new Error(`reply timed out after ${timeoutMs}ms`);
}

// 使用方式
it('chatbot 能正確回覆問題', async () => {
  const beforeCount = Number(await evalJs(
    `document.querySelectorAll('.message.bot').length`
  ));
  await fill('#input', '什麼是 OpenCLI？');
  await keys('Enter');
  const reply = await waitReplyComplete(beforeCount);
  expect(reply).toContain('OpenCLI');
});

陷阱三：Windows 路徑與換行問題

截圖路徑的反斜線問題

Windows 的路徑分隔符是 \，但在 shell（PowerShell / cmd）中反斜線是轉義字元。 當你直接在 shell 輸入 artifacts\login.png，shell 會把 \l 當作 l 的轉義序列，導致 OpenCLI 收到的路徑是錯的。

❌ 錯誤示範 vs ✅ 正確寫法 
# ❌ 錯誤：Windows shell 中使用反斜線路徑
# PowerShell 會把 artifactslogin.png 解析為 artifacts<Tab>login.png
opencli browser e2e screenshot artifactslogin.png

# ❌ 錯誤：多行指令換行方式混用
opencli browser e2e   open http://localhost:8090  # Bash 換行，在 PowerShell 中無效
✅ 統一使用正斜線 + 正確換行方式 
# ✅ 正確：一律使用正斜線（Windows 和 POSIX 都接受）
opencli browser e2e screenshot artifacts/login.png

# ✅ PowerShell 多行：用反引號 ` 換行
opencli browser e2e `
  open http://localhost:8090

# ✅ Bash 多行：用反斜線  換行
opencli browser e2e \
  open http://localhost:8090

Node.js 程式碼中的路徑處理

在 TypeScript helper 中，path.join() 在 Windows 上會產生反斜線路徑， 傳給 OpenCLI 可能出問題。最安全的做法是直接用 template literal 搭配正斜線。

Node.js 中的跨平台路徑處理 
// ✅ 在 Node.js 程式碼中：用 path.join 自動處理路徑分隔符
import path from 'node:path';

// path.join 在 Windows 上產生 ，但我們需要 /
// 改用 path.posix.join 或手動替換
const artifactPath = path.join('artifacts', 'login.png').replace(/\\/g, '/');

// 或直接用 template literal 搭配正斜線（最簡單）
const screenshotPath = `artifacts/${testName}-step${step}.png`;

// 在 helpers/opencli.ts 的 screenshot() 函數中應用
export async function screenshot(name: string) {
  // 永遠使用正斜線，確保跨平台一致
  const p = `artifacts/${name}`.replace(/\\/g, '/');
  return must(await browser('screenshot', p));
}

spawn 與 quoteForShell 的必要性

這個問題在第 8 章已詳細說明：child_process.spawn 搭配 shell: true 在 Windows 上不會自動為含空白的參數加引號。當截圖路徑含有空白（例如 my artifacts/test.png）， 必須用 quoteForShell 處理。

quoteForShell 保護含空白的路徑（參考第 8 章） 
// ✅ quoteForShell 函式（參考第 8 章）確保 Windows spawn 正確處理路徑
function quoteForShell(a: string): string {
  if (a === '' || /[\s"'`$&|<>(){};,?*^!%]/.test(a)) {
    return '"' + a.replace(/(["\\])/g, '\\$1') + '"';
  }
  return a;
}

// 當路徑含有空白或特殊字元時，quoteForShell 自動加上引號
const p = spawn('opencli', ['browser', 'e2e', 'screenshot', 'my artifacts/test.png'].map(quoteForShell), {
  shell: true,
});
// Windows cmd.exe 收到：opencli browser e2e screenshot "my artifacts/test.png"
黃金法則：路徑命名避免空白

最省事的做法：截圖目錄和測試名稱都不要用空白，改用連字符 - 或底線 _。 路徑不含空白，quoteForShell 也不需要加引號，跨平台零煩惱。

Debug 技巧一：state 快照

opencli browser <session> state 輸出當前頁面的 DOM 結構（預設為 Accessibility Tree 格式）。 這是最快的「我到底在哪個頁面、頁面上有什麼元素」診斷工具。

state 指令的三種輸出格式 
# 預設格式：ax（Accessibility Tree，適合斷言文字內容）
opencli browser e2e state

# DOM 原始 HTML（適合排查 selector 問題）
opencli browser e2e state --source dom

# 只輸出 URL 和 title（快速確認頁面）
opencli browser e2e state --source meta

在測試中插入 state 快照

當測試失敗但截圖看不出原因時，在關鍵步驟前後插入 console.log(await state())， 可以看到「那個時間點」的完整 DOM 結構：

在測試中插入 state 快照 
// 在測試中插入 state 快照，查看當前 DOM 結構
it('能顯示搜尋結果', async () => {
  await open('http://localhost:8090/search');
  await fill('#query', 'OpenCLI');
  await click('button.search-btn');

  // 🔍 Debug：印出當前 DOM（預設 ax 格式，適合閱讀）
  const dom = await state();
  console.log('=== 點擊搜尋後 DOM ===');
  console.log(dom);

  await browser('wait', 'selector', '.result-item', '--timeout', '10000');
  expect(dom).toContain('搜尋結果');
});

封裝 debugState helper

為了不讓 console.log 爆炸（完整 DOM 可能超過 10000 字）， 建議封裝一個 debugState helper，限制輸出長度並加上標籤：

debugState helper（限制輸出長度） 
// TypeScript helper：封裝 state 呼叫，加上 label 方便在 log 中辨識
async function debugState(label: string) {
  const dom = await state();
  console.log(`\n[${label}] DOM 快照 (${new Date().toISOString()}):`);
  console.log(dom.slice(0, 2000));  // 只印前 2000 字，避免 log 爆炸
  console.log('---');
  return dom;
}

// 使用方式
it('登入流程', async () => {
  await open('http://localhost:8090/login');
  await debugState('開啟登入頁');

  await fill('#email', 'user@test.com');
  await debugState('填入 email 後');

  await click('button[type="submit"]');
  await browser('wait', 'text', '登入成功', '--timeout', '10000');
  await debugState('登入成功後');
});

Debug 技巧二：截圖時間軸

與其在失敗後猜測「當時頁面長什麼樣」，不如在關鍵步驟前後截圖，建立一條視覺時間軸。 CI 失敗時，下載 artifacts 資料夾，按截圖序號逐張查看，問題通常一眼就能看出。

建立 debugShot Helper

統一管理截圖的 helper，自動為截圖加上測試名稱和步驟序號，方便事後整理：

helpers/debug.ts：debugShot helper 
// helpers/debug.ts：統一管理截圖的 helper
import { browser } from './opencli';

let _shotCounter = 0;
let _currentTestName = '';

// 在 beforeEach 中重置計數器和測試名稱
export function initDebugShots(testName: string) {
  _shotCounter = 0;
  _currentTestName = testName.replace(/[^a-zA-Z0-9一-鿿]/g, '_');
}

// 截圖命名慣例：${testName}-step${n}.png
export async function debugShot(label?: string) {
  _shotCounter++;
  const step = String(_shotCounter).padStart(2, '0');
  const suffix = label ? `-${label.replace(/\s+/g, '_')}` : '';
  const filename = `${_currentTestName}-step${step}${suffix}.png`;
  await browser('screenshot', `artifacts/${filename}`);
  console.log(`📸 ${filename}`);
}
在測試中使用 debugShot 
import { initDebugShots, debugShot } from '../helpers/debug';

describe('結帳流程', () => {
  beforeEach(async (ctx) => {
    initDebugShots(ctx.task.name);
  });

  it('能完成商品結帳', async () => {
    await open('http://localhost:8090/cart');
    await debugShot('購物車頁面');        // → 結帳流程-step01-購物車頁面.png

    await click('button.checkout');
    await browser('wait', 'selector', '.checkout-form', '--timeout', '8000');
    await debugShot('結帳表單出現');      // → 結帳流程-step02-結帳表單出現.png

    await fill('#card-number', '4111111111111111');
    await fill('#expiry', '12/28');
    await debugShot('填入卡號後');        // → 結帳流程-step03-填入卡號後.png

    await click('button.pay-now');
    await browser('wait', 'text', '付款成功', '--timeout', '15000');
    await debugShot('付款完成');          // → 結帳流程-step04-付款完成.png
  });
});

測試失敗時自動截圖

搭配 Vitest 的 afterEach hook，在測試失敗時自動截圖保留現場。 這個 hook 放在 helpers/debug.ts 並在 vitest.config.ts 的 setupFiles 中引入，讓所有 spec 自動享有這個保護：

測試失敗時自動截圖（afterEach hook） 
// ✅ 最佳實踐：測試失敗時自動截圖保留現場
import { afterEach } from 'vitest';
import { browser } from './opencli';

afterEach(async (ctx) => {
  if (ctx.task.result?.state === 'fail') {
    const safeName = ctx.task.name.replace(/[^a-zA-Z0-9一-鿿]/g, '_');
    await browser('screenshot', `artifacts/FAILED-${safeName}-${Date.now()}.png`);
    console.error(`失敗截圖已存至 artifacts/FAILED-${safeName}.png`);
  }
});
截圖命名慣例
  • 正常步驟截圖：{testName}-step{n}-{label}.png（例如 登入流程-step01-開啟頁面.png）
  • 失敗截圖：FAILED-{testName}-{timestamp}.png
  • 所有截圖統一放 artifacts/，CI 透過 upload-artifact 保存

Debug 技巧三：逐步縮小問題範圍

用 it.only 隔離單一測試

懷疑某個測試失敗是因為前面的測試污染，先用 it.only 單獨跑它， 確認它是否能獨立通過：

用 it.only 隔離問題測試 
// ✅ 用 it.only 隔離單一測試，避免其他 spec 干擾
describe('搜尋功能', () => {
  it('能搜尋關鍵字', async () => {
    // 這個測試正常
  });

  it.only('搜尋結果能分頁', async () => {
    // 只跑這一個測試，確認是否是單獨問題
    // 確認後記得移除 .only，否則 CI 會跑不完整
  });

  it('能篩選結果', async () => {
    // 這個測試被跳過
  });
});
記得移除 .only

it.only 只是除錯工具，確認問題後必須移除。 若忘記移除並推送到 CI，其餘測試都會被跳過，CI 報告會顯示「只跑了 1 個測試」。 可以在 CI 的 lint 步驟加入 grep -r "it.only\|test.only\|describe.only" 防呆。

verbose Reporter 看詳細輸出

預設的 reporter 只顯示失敗的測試。切換到 verbose 可以看到每個 it 的執行時間，快速找出哪一步驟特別慢（往往就是 timeout 的源頭）：

verbose 模式與按 spec 執行 
# 使用 verbose reporter 看每一個 test 的詳細輸出
npx vitest run --reporter=verbose

# 同時輸出 verbose 和 JUnit 報告
npx vitest run --reporter=verbose --reporter=junit --outputFile=artifacts/junit.xml

# 只跑單一 spec 檔案
npx vitest run specs/02-search.spec.ts

# 只跑名稱符合 pattern 的測試（支援 regex）
npx vitest run --reporter=verbose -t "分頁"

在 Terminal 手動重現問題

這是最強力的除錯方式：不跑測試，直接在 terminal 逐行輸入 opencli browser session 指令，觀察每一步的反應。可以即時修改指令、即時看結果，比跑完整測試快 10 倍：

Terminal 手動除錯流程 
# 直接在 terminal 手動執行 opencli 指令重現問題
# 這是最快的除錯方式，不需要跑完整測試

# 1. 開啟頁面
opencli browser e2e open http://localhost:8090/search

# 2. 查看當前 DOM（確認 selector 是否正確）
opencli browser e2e state

# 3. 嘗試點擊（如果失敗，state 會顯示原因）
opencli browser e2e click "搜尋"

# 4. 等待元素出現，確認 wait 指令是否有效
opencli browser e2e wait selector .result-item --timeout 5000

# 5. 截圖確認視覺狀態
opencli browser e2e screenshot artifacts/debug-manual.png

# 6. 用 ax 格式看 accessibility tree（適合找 label/role）
opencli browser e2e state --source ax

# 7. 用 dom 格式看原始 HTML（適合找 class/id）
opencli browser e2e state --source dom
手動除錯的節奏

建議開兩個 terminal：左邊輸入 opencli 指令，右邊開著瀏覽器視窗（非 headless 模式）。 每次執行指令後，右邊的瀏覽器會即時反映操作結果，等於有了一個「視覺化的 REPL」。

快速診斷 Checklist

遇到 E2E 測試問題，先對照下表找到對應的解法：

症狀 可能原因 解法
單獨跑通，合併跑失敗 Session 污染（前一個 spec 留下狀態） afterAll session close，或改用不同 session 名稱
偶爾失敗，截圖有 spinner 時序競爭（click 後頁面還沒更新） click 後加 wait selector / wait text
CI 失敗，本機通過 CI 機器較慢，timeout 不夠長 增加 testTimeout 或 wait --timeout 的值
截圖路徑報錯（Windows） 路徑用了反斜線 \ 一律改用正斜線 /
含空白的 arg 被切斷 spawn shell:true 不自動 quote 套用 quoteForShell（參考第 8 章）
APP_URL / BASE_URL 讀到 / Vitest 繼承 Vite，強制覆蓋 BASE_URL 改用 APP_URL 或任何非保留名稱
eval 指令只執行第一行 多行 JS 被 shell 截斷 改為單行 JS（用逗號運算子或 Array 方法）
wait selector 一直 timeout selector 錯誤或元素實際上不存在 先 state --source dom 確認 HTML 結構
Streaming 回覆 assert 失敗 回覆尚未完成就讀取 改用 waitReplyComplete 穩定偵測完成（第 7 章）
不知道當前頁面長什麼樣 （除錯出發點） 先執行 state 或截圖，再對照 DOM 排查

本章小結

三大陷阱有清晰的識別方式與對應解法：

  • Session 污染：每個 suite 都要有 afterAll cleanup，或使用獨立的 session 名稱
  • 時序競爭：click 之後永遠先 wait，再 assert——這是 E2E 測試最重要的習慣
  • Windows 路徑：路徑一律正斜線、spawn 參數一律 quoteForShell、環境變數不要用 BASE_URL

三大 Debug 技巧的使用優先順序建議：先看截圖（視覺最直觀）→ 再看 state 快照（DOM 細節）→ 最後在 terminal 手動逐步執行（最精確）。大多數問題在第一步截圖就能看出答案。
