第 9 章 · Part 3：E2E 測試

撰寫第一個 E2E 測試

上一章建立了 Vitest + OpenCLI 的測試基礎架構，這一章我們把它用起來。 從一個真實的登入流程出發，逐步拆解每個測試步驟，學習如何找元素、填表單、 斷言結果，以及在失敗時用截圖快速定位問題。

1. 測試目標：一個真實的登入流程

為什麼第一個 E2E 測試要選「登入」？因為登入流程具備幾乎所有 E2E 測試的共同元素： 頁面導航、表單填寫、按鈕點擊、非同步等待、URL 跳轉、狀態驗證。 把登入流程測好，後續所有測試都是同一套思路的延伸。

我們要驗證的行為如下：

步驟 操作 預期結果
1 開啟 /login 頁面顯示 email、password 輸入框
2 填入合法帳號密碼，點擊送出 頁面出現「歡迎」文字（非同步）
3 驗證登入後狀態 頁面包含「儀表板」與「登出」
4 點擊登出 跳轉回 /login，表單再度出現
測試目標概覽（偽程式碼） 
// 我們要驗證的三個關鍵行為：
// 1. /login 頁面正確渲染登入表單
// 2. 填入合法帳號密碼後，成功跳轉至儀表板
// 3. 點擊登出後，回到 /login

// 每一步都有明確的「輸入 → 操作 → 斷言」結構

2. 測試檔案結構

在 e2e/specs/ 資料夾建立 01-login.spec.ts。 用數字前綴命名是個好習慣——Vitest 預設按字母順序執行，前綴讓執行順序一目了然， 也方便之後插入新的測試檔案。

e2e/specs/01-login.spec.ts — 完整版本 
import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import * as cli from '../helpers/opencli';

const BASE_URL = process.env.BASE_URL ?? 'http://localhost:3000';

describe('登入流程', () => {
  // 整個 describe 只開一次瀏覽器分頁
  beforeAll(async () => {
    await cli.open(`${BASE_URL}/login`);
  });

  // 測試結束後關閉 session，釋放資源
  afterAll(async () => {
    await cli.browser('session', 'close');
  });

  it('應顯示登入表單', async () => {
    const html = await cli.state();
    expect(html).toContain('type="email"');
    expect(html).toContain('type="password"');
  });

  it('填入帳號密碼後應登入成功', async () => {
    await cli.fill('input[type="email"]',    'user@example.com');
    await cli.fill('input[type="password"]', 'secret123');
    await cli.click('button[type="submit"]');
    await cli.browser('wait', 'text', '歡迎', '--timeout', '10000');
  });

  it('登入後應顯示儀表板', async () => {
    const html = await cli.state();
    expect(html).toContain('儀表板');
    expect(html).toContain('登出');
  });

  it('登出後應回到登入頁', async () => {
    await cli.click('a[href*="logout"], button.logout');
    await cli.browser('wait', 'selector', 'input[type="email"]', '--timeout', '8000');
    const html = await cli.state();
    expect(html).toContain('type="email"');
  });
});
describe / it / beforeAll / afterAll 的職責分工
  • describe：把相關的 it 群組在一起，提供語意上的分類
  • beforeAll：整個 describe 執行前跑一次，適合做一次性的準備工作（開瀏覽器、登入）
  • afterAll：整個 describe 執行後跑一次，適合清理資源（關閉 session）
  • it（或 test）：一個獨立的測試案例，只測一件事

3. 逐步拆解每個 it 區塊

現在我們把完整的 spec 拆開來看，理解每一個 it 裡面發生了什麼事。

Step 1：驗證登入表單存在

第一個 it 最單純：開啟頁面之後，確認 DOM 裡有 email 和 password 的輸入框。 cli.state() 會回傳當前頁面的完整 HTML 字串，我們用 toContain 斷言。

it #1：確認表單元素存在 
it('應顯示登入表單', async () => {
  // cli.state() 回傳當前頁面的 HTML（字串）
  const html = await cli.state();

  // 斷言：頁面裡存在 email 輸入欄位
  expect(html).toContain('type="email"');
  // 斷言：頁面裡存在 password 輸入欄位
  expect(html).toContain('type="password"');
});
為什麼用 state() 而不是 find()?

cli.state() 一次拿回整個頁面 HTML，適合做「頁面整體狀態」的斷言。 如果你需要驗證某個特定元素的屬性或文字，也可以搭配 cli.evalJs() 精確讀取。選擇哪個，取決於你想驗證「整體」還是「細節」。

Step 2：填寫表單並登入

第二個 it 是整個測試的核心操作：填表單 → 點送出 → 等待結果。 cli.fill() 接受 CSS 選擇器和填入值；cli.click() 觸發點擊； cli.browser('wait', 'text', ...) 等待特定文字出現，這是處理非同步跳轉最可靠的方式。

it #2：填表單 + 等待登入成功 
it('填入帳號密碼後應登入成功', async () => {
  // 1. 填寫 email 欄位
  await cli.fill('input[type="email"]', 'user@example.com');

  // 2. 填寫密碼欄位
  await cli.fill('input[type="password"]', 'secret123');

  // 3. 點擊送出按鈕
  await cli.click('button[type="submit"]');

  // 4. 等待「歡迎」文字出現，確認登入成功（最多 10 秒）
  await cli.browser('wait', 'text', '歡迎', '--timeout', '10000');
});
不要用 sleep 等待，要用 wait

你可能會想到用 await new Promise(r => setTimeout(r, 3000)) 等 3 秒。 這樣做有兩個問題：一是慢，明明 500ms 就完成了卻等了 3 秒；二是脆弱， 如果網路變慢超過 3 秒就會失敗。wait text 會持續輪詢直到條件成立或超時， 既快又可靠。

Step 3：驗證儀表板頁面

登入成功後，驗證當前頁面確實是儀表板，而不是停留在錯誤頁或其他位置。

it #3：確認儀表板內容 
it('登入後應顯示儀表板', async () => {
  // 登入成功後取得當前頁面 HTML
  const html = await cli.state();

  // 應包含儀表板標題
  expect(html).toContain('儀表板');

  // 應包含登出入口（確認使用者狀態正確）
  expect(html).toContain('登出');
});

Step 4：登出並確認跳轉

最後一步：觸發登出，等待 email 輸入框再次出現（代表已回到登入頁）， 再次確認頁面狀態。注意選擇器 'a[href*="logout"], button.logout' 使用逗號 分隔兩個選擇器，相容不同網站的登出按鈕實作方式。

it #4：登出並驗證跳回登入頁 
it('登出後應回到登入頁', async () => {
  // 點擊登出連結或按鈕（相容不同網站的選擇器寫法）
  await cli.click('a[href*="logout"], button.logout');

  // 等待登入表單再次出現，確認已跳轉回 /login
  await cli.browser('wait', 'selector', 'input[type="email"]', '--timeout', '8000');

  const html = await cli.state();
  expect(html).toContain('type="email"');
});

確認開發伺服器已在 http://localhost:3000 執行後， 在另一個終端機執行測試指令：

# 搭配環境變數（指向 staging 環境）

失敗時的輸出

當測試失敗，Vitest 會精確指出哪個 it 失敗、錯誤原因， 以及呼叫堆疊的位置：

測試失敗範例 
 FAIL  e2e/specs/01-login.spec.ts (5.14 s)
  登入流程
    ✓ 應顯示登入表單 (398 ms)
    ✗ 填入帳號密碼後應登入成功 (10042 ms)
      → Error: timeout exceeded waiting for text "歡迎"
        at waitText (helpers/opencli.ts:61:11)
        at 01-login.spec.ts:23:5
    - 登入後應顯示儀表板 (skipped)
    - 登出後應回到登入頁 (skipped)

 Test Files  1 failed (1)
 Tests       1 failed | 3 skipped (4)
讀懂失敗訊息
  • → Error: timeout exceeded waiting for text "歡迎"：等了 10 秒，頁面始終沒出現「歡迎」——可能是後端返回錯誤，或選擇器不對
  • skipped：因為前面的 it 失敗，後續的 it 被跳過——這是正常行為，避免在錯誤狀態下繼續執行
  • 最後一行 Duration 約等於 timeout 設定值，代表是「等到超時」而不是「立刻失敗」

5. 加上截圖輔助除錯

文字訊息說「timeout」，但你不知道當下頁面長什麼樣子。 截圖是 E2E 測試除錯最直覺的工具——一張截圖勝過千行 log。

手動在失敗點截圖

最直接的做法：在你懷疑會失敗的地方，用 try/catch 包住操作， 失敗時立刻截圖。

手動在失敗點截圖 
it('填入帳號密碼後應登入成功', async () => {
  await cli.fill('input[type="email"]',    'user@example.com');
  await cli.fill('input[type="password"]', 'secret123');

  // 填寫後截圖，確認表單狀態正確
  await cli.screenshot('02-form-filled.png');

  await cli.click('button[type="submit"]');

  try {
    await cli.browser('wait', 'text', '歡迎', '--timeout', '10000');
  } catch (e) {
    // 失敗時截圖，保留現場
    await cli.screenshot('02-login-failed.png');
    throw e;
  }
});

afterEach 自動截圖模式

更系統化的做法：用 afterEach 鉤子，在每個 it 失敗後自動截圖， 不需要在每個 test case 裡手動加 try/catch。

afterEach 自動截圖（放在 setup 或 spec 最上方） 
import { afterEach } from 'vitest';
import * as cli from '../helpers/opencli';

// 每個 it 結束後，若失敗就自動截圖
afterEach(async (ctx) => {
  if (ctx.task.result?.state === 'fail') {
    const safeName = ctx.task.name.replace(/\s+/g, '_');
    await cli.screenshot(`FAILED-${safeName}-${Date.now()}.png`);
    console.error(`截圖已儲存：artifacts/FAILED-${safeName}-*.png`);
  }
});
截圖儲存在哪裡？

cli.screenshot() helper 已在第 8 章設計為儲存至 e2e/artifacts/ 資料夾。 記得把 e2e/artifacts/ 加入 .gitignore，避免把截圖 commit 進去。 本地開發時直接打開圖檔檢查即可。

CI 環境上傳截圖

在 CI 流程中，測試失敗產生的截圖可以上傳為 artifact，方便事後查看。 以 GitHub Actions 為例：

GitHub Actions：上傳截圖 artifact 
# .github/workflows/e2e.yml 節錄
- name: Upload screenshots on failure
  if: failure()
  uses: actions/upload-artifact@v4
  with:
    name: e2e-screenshots
    path: e2e/artifacts/*.png
    retention-days: 7

6. 測試的三個好習慣

好習慣一：每個 it 只測一件事

每個 it 的名稱就是它的規格說明，名稱應該能完整描述「在什麼情況下， 預期什麼行為」。如果你的 it 名稱裡出現「並且」，通常代表你塞了太多東西進去， 應該拆成兩個 it。

範例 問題
it('登入並進入儀表板並驗證使用者名稱') 三件事混在一起，哪裡壞掉不容易定位
it('填入帳號密碼後應登入成功') 一件事，清楚明確
it('登入後應顯示儀表板') 一件事，清楚明確

好習慣二：用 beforeAll 做一次性準備

每個 it 都呼叫 cli.open() 是常見的反模式。 開瀏覽器、載入頁面本身就需要時間，重複做只會讓測試變慢， 而且在某些情況下還會造成 session 衝突。

❌ 反模式 vs ✅ 正確做法 
// ❌ 反模式：每個 it 都重新打開瀏覽器（慢、資源浪費）
describe('登入流程', () => {
  it('應顯示登入表單', async () => {
    await cli.open('http://localhost:3000/login'); // 重複開啟
    const html = await cli.state();
    expect(html).toContain('type="email"');
  });

  it('填入帳號密碼', async () => {
    await cli.open('http://localhost:3000/login'); // 又再開一次！
    await cli.fill('input[type="email"]', 'user@example.com');
    // ...
  });
});
✅ 正確做法：beforeAll 只開一次 
// ✅ 正確做法：beforeAll 只開一次，所有 it 共用同一個 session
describe('登入流程', () => {
  beforeAll(async () => {
    await cli.open('http://localhost:3000/login'); // 只開一次
  });

  afterAll(async () => {
    await cli.browser('session', 'close');         // 最後統一關
  });

  it('應顯示登入表單', async () => { /* ... */ });
  it('填入帳號密碼後應登入成功', async () => { /* ... */ });
});
注意：it 之間有執行順序依賴時才共用 session

共用 session 的前提是：後面的 it 依賴前面的 it 所建立的狀態（例如登入狀態）。 如果你的 it 之間完全獨立，應該考慮用 beforeEach 各自準備初始狀態， 避免一個 it 改變狀態後影響下一個。

好習慣三：斷言要明確具體

模糊的斷言幾乎永遠是通過的，但它沒有驗證到任何有意義的東西。 好的斷言應該精確到「這個頁面特有的內容」。

❌ 模糊斷言（幾乎永遠通過） 
// ❌ 模糊斷言：通過了，但沒有驗證到任何有意義的東西
const html = await cli.state();
expect(html).toBeTruthy();          // 頁面有內容就過，幾乎永遠是 true
expect(html.length).toBeGreaterThan(0); // 同上，毫無意義
✅ 具體斷言（真正驗證行為） 
// ✅ 具體斷言：明確說出期望的內容
const html = await cli.state();
expect(html).toContain('歡迎，Porter');          // 精確到使用者名稱
expect(html).toContain('data-page="dashboard"'); // 確認是儀表板頁面
expect(html).not.toContain('type="password"');   // 確認已脫離登入頁

7. 加第二個測試：搜尋功能

登入流程測完了，我們接著加第二個測試：搜尋功能。 這個範例展示一個重要的現實情境——測試功能本身需要先完成登入才能使用。

e2e/specs/02-search.spec.ts — 完整版本 
import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import * as cli from '../helpers/opencli';

const BASE_URL = process.env.BASE_URL ?? 'http://localhost:3000';

describe('搜尋功能', () => {
  beforeAll(async () => {
    // 搜尋功能需要先登入，beforeAll 先完成登入流程
    await cli.open(`${BASE_URL}/login`);
    await cli.fill('input[type="email"]',    'user@example.com');
    await cli.fill('input[type="password"]', 'secret123');
    await cli.click('button[type="submit"]');
    await cli.browser('wait', 'text', '歡迎', '--timeout', '10000');

    // 登入後前往搜尋頁
    await cli.open(`${BASE_URL}/search`);
  });

  afterAll(async () => {
    await cli.browser('session', 'close');
  });

  it('應顯示搜尋輸入框', async () => {
    const html = await cli.state();
    expect(html).toContain('placeholder');
    expect(html).toContain('search');
  });

  it('輸入關鍵字後應顯示結果', async () => {
    await cli.fill('input[type="search"]', 'Claude');
    await cli.click('button[type="submit"]');

    // 等待結果列表出現
    await cli.browser('wait', 'selector', '.search-results', '--timeout', '8000');

    const html = await cli.state();
    expect(html).toContain('Claude');
  });

  it('清空關鍵字後應重設結果', async () => {
    // 清空搜尋欄（用空字串覆蓋）
    await cli.fill('input[type="search"]', '');
    await cli.click('button[type="submit"]');

    await cli.browser('wait', 'selector', '.empty-state', '--timeout', '5000');
    const html = await cli.state();
    expect(html).toContain('empty-state');
  });
});

Session 策略：獨立 vs 共用

當你有多個 spec 檔案時，需要決定 session 如何管理： 是每個 spec 各自擁有獨立的 session，還是所有 spec 共用同一個已登入的 session？

兩種 Session 策略比較 
// 策略 A：獨立 session（每個 spec 完全隔離，互不干擾）
// helpers/opencli.ts 中 SESSION 名稱固定為 'e2e'，
// 每個 spec 的 afterAll 都呼叫 session close，
// 下一個 spec 的 beforeAll 再重新開啟。

// 策略 B：共用 session（跨 spec 保留瀏覽器狀態）
// 在 vitest.setup.ts 裡只開一次，globalThis 傳遞
// vitest.setup.ts
import * as cli from './helpers/opencli';
const BASE_URL = process.env.BASE_URL ?? 'http://localhost:3000';

beforeAll(async () => {
  await cli.open(`${BASE_URL}/login`);
  await cli.fill('input[type="email"]',    'user@example.com');
  await cli.fill('input[type="password"]', 'secret123');
  await cli.click('button[type="submit"]');
  await cli.browser('wait', 'text', '歡迎', '--timeout', '10000');
});

afterAll(async () => {
  await cli.browser('session', 'close');
});
策略 優點 缺點 適合場景
獨立 session 每個 spec 完全隔離，互不干擾 每個 spec 都要重新登入，速度較慢 spec 數量少、或需要測試不同登入狀態
共用 session 登入一次就好，速度較快 前面的 spec 出錯可能影響後面的 spec 所有測試都在同一個登入使用者下執行

執行多個 spec

執行所有 spec 或指定 spec 
# 執行所有 spec 檔案（按檔名字母順序）
npx vitest run e2e/specs/

# 只跑特定 spec
npx vitest run e2e/specs/02-search.spec.ts

# 開發模式：監聽變更自動重跑
npx vitest watch e2e/specs/
spec 命名規範建議

用數字前綴（01-、02-）明確控制執行順序。 如果 spec 之間有依賴關係（例如必須先執行登入測試才跑搜尋測試）， 數字前綴讓順序變得顯而易見，也方便日後插入新的測試檔案。

小結

本章從一個真實的登入流程出發，示範了完整 E2E 測試的撰寫方式：

  • 用 describe + beforeAll + afterAll 組織測試結構，管理 session 生命週期
  • 每個 it 對應一個明確的行為：找元素、填表單、點擊、等待非同步、斷言
  • 用 wait text / wait selector 處理非同步，絕對不用 sleep
  • 用截圖（手動或 afterEach 自動）保留失敗現場，快速定位問題
  • 三個好習慣：每個 it 只測一件事、beforeAll 做一次性準備、斷言要具體
