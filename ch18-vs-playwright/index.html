第 18 章 · Part 6：比較與實戰

OpenCLI vs Playwright

兩個工具都能操控瀏覽器，但設計哲學截然不同。本章深度比較它們的定位、 程式碼模式、效能差異與遷移策略，幫助你在對的場景選擇對的工具。

18.1 兩個工具的定位

理解這兩個工具最快的方式，是看它們如何表達「同一個需求」：

OpenCLI 的表達方式

opencli twitter trending

我要「Twitter 的趨勢」— 語義清晰，意圖即指令。

Playwright 的表達方式

page.goto(...)
page.waitForSelector(...)
page.$$eval(...)

導航到 URL → 等那個元素 → 點這個按鈕 → 擷取文字。

OpenCLI 是以平台語義為中心的 CLI 工具。它的 Adapter 層封裝了每個平台的知識—— Twitter 怎麼取趨勢、GitHub 怎麼搜尋 Repo、Bilibili 怎麼繞過反爬機制——這些細節都在 Adapter 裡， 使用者只需要知道「我想要什麼」。

Playwright 是底層瀏覽器自動化框架。它提供完整的 DOM 操作、網路攔截、截圖等能力， 但所有平台邏輯都要自行實作。這帶來了極大的靈活度，同時也意味著更高的開發成本與維護負擔。

18.2 核心設計哲學比較

維度 OpenCLI Playwright
抽象層次 語義指令（trending、search） DOM 操作（selector、click、waitFor）
平台支援 內建 80+ Adapter，開箱即用 無內建平台知識，需全部自行實作
學習曲線 CLI 即用，10 分鐘上手 需學 API + CSS 選擇器 + 非同步控制
維護成本 平台改版由 Adapter 社群維護 平台改版需自行更新所有 selector
靈活度 受限於 Adapter 提供的指令集 完全自由，可操作任意頁面行為
適合場景 資料擷取、平台互動、AI Agent 工具 E2E 測試、自訂 UI 流程、截圖 / PDF
除錯難度 結構化錯誤訊息，明確指向問題 需自行追蹤 DOM 狀態與時序問題

18.3 同一任務的程式碼對比

紙上比較不如程式碼直觀。以下三個真實案例，讓你親眼看見兩種方式的差距。

案例一：取得 Twitter 熱門話題

OpenCLI — 1 行 
# 1 行指令，取得 Twitter 熱門話題 Top 10
opencli twitter trending --limit 10
Playwright — 約 25 行 
import { chromium } from 'playwright';

async function getTwitterTrending(): Promise<string[]> {
  const browser = await chromium.launch({ headless: true });
  const context = await browser.newContext({
    userAgent: 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36'
  });
  const page = await context.newPage();

  // 需要先登入，否則 Twitter 會導向登入頁
  await page.goto('https://twitter.com/explore/tabs/trending');
  await page.waitForSelector('[data-testid="trend"]', { timeout: 10000 });

  const trends = await page.$$eval('[data-testid="trend"]', items =>
    items.map(el => {
      const name = el.querySelector('[dir="ltr"] > span')?.textContent?.trim() ?? '';
      const count = el.querySelector('[dir="ltr"]:last-child')?.textContent?.trim() ?? '';
      return { name, count };
    })
  );

  await browser.close();
  // 過濾空值並取前 10 筆
  return trends
    .filter(t => t.name.length > 0)
    .slice(0, 10)
    .map(t => t.name);
}

getTwitterTrending().then(console.log).catch(console.error);
ℹ️
為什麼 Playwright 版本更複雜？

Twitter 需要登入才能看趨勢、selector 隨版本改變（data-testid 名稱常變動）、 User-Agent 偽裝避免被識別為 Bot。這些知識都已封裝在 OpenCLI 的 Twitter Adapter 中。

案例二：搜尋 GitHub 熱門 Repo

OpenCLI — 1 行帶參數 
# 1 行帶參數，搜尋 GitHub 熱門 TypeScript 專案
opencli github trending --language typescript --since weekly --limit 20
Playwright — 約 35 行 
import { chromium } from 'playwright';

interface GitHubRepo {
  name: string;
  description: string;
  stars: string;
  language: string;
  starsThisWeek: string;
}

async function getGitHubTrending(language: string, since: string): Promise<GitHubRepo[]> {
  const browser = await chromium.launch({ headless: true });
  const page = await browser.newPage();

  const url = `https://github.com/trending/${language}?since=${since}`;
  await page.goto(url);

  // 等待動態載入完成（GitHub 使用 Turbo/SPA 架構）
  await page.waitForSelector('article.Box-row', { timeout: 15000 });

  const repos = await page.$$eval('article.Box-row', (items: Element[]) =>
    items.map(el => ({
      name: el.querySelector('h2 a')?.textContent?.replace(/\s+/g, ' ').trim() ?? '',
      description: el.querySelector('p.col-9')?.textContent?.trim() ?? '',
      stars: el.querySelector('a[href$="/stargazers"]')?.textContent?.trim() ?? '0',
      language: el.querySelector('[itemprop="programmingLanguage"]')?.textContent?.trim() ?? '',
      starsThisWeek: el.querySelector('.float-sm-right')?.textContent?.trim() ?? ''
    }))
  );

  await browser.close();
  // 過濾掉名稱為空的條目（廣告或其他非 Repo 元素）
  return repos.filter(r => r.name.length > 0).slice(0, 20);
}

getGitHubTrending('typescript', 'weekly')
  .then(repos => console.log(JSON.stringify(repos, null, 2)))
  .catch(console.error);

案例三：Bilibili 影片評論擷取

OpenCLI — 2 行 
# 搜尋影片
opencli bilibili search "TypeScript 教學" --limit 5

# 取得第一支影片的評論（bvid 從上一步結果取得）
opencli bilibili comments BV1xx411c79H --limit 50
Playwright — 約 50 行（含反爬處理） 
import { chromium } from 'playwright';

// Bilibili 有反爬機制：需要 Cookie、User-Agent 偽裝、隨機延遲
async function getBilibiliComments(bvid: string): Promise<object[]> {
  const browser = await chromium.launch({
    headless: false, // Bilibili 偵測 headless，需設為 false
    args: ['--disable-blink-features=AutomationControlled']
  });
  const context = await browser.newContext({
    userAgent: 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120.0.0.0',
    // 需要預先匯入登入後的 Cookie 檔案
    storageState: './bilibili-storage.json'
  });
  const page = await context.newPage();

  // 隱藏 webdriver 特徵
  await page.addInitScript(() => {
    Object.defineProperty(navigator, 'webdriver', { get: () => undefined });
  });

  await page.goto(`https://www.bilibili.com/video/${bvid}`);

  // 等待頁面完全載入（Bilibili 是重度 SPA）
  await page.waitForLoadState('networkidle', { timeout: 20000 });
  await page.waitForSelector('.comment-list', { timeout: 15000 });

  // 需要滾動觸發懶載入
  for (let i = 0; i < 5; i++) {
    await page.evaluate(() => window.scrollBy(0, 600));
    await page.waitForTimeout(800); // 必須等待，否則內容不載入
  }

  const comments = await page.$$eval('.comment-item', items =>
    items.map(el => ({
      user: el.querySelector('.user-name')?.textContent?.trim() ?? '',
      content: el.querySelector('.comment-content')?.textContent?.trim() ?? '',
      likes: el.querySelector('.like-count')?.textContent?.trim() ?? '0',
      time: el.querySelector('.comment-time')?.textContent?.trim() ?? ''
    }))
  );

  await browser.close();
  return comments.slice(0, 50);
}

getBilibiliComments('BV1xx411c79H')
  .then(data => console.log(JSON.stringify(data, null, 2)))
  .catch(console.error);
⚠️
Bilibili 的反爬機制

Bilibili 會偵測 navigator.webdriver、禁止 headless 模式、要求有效 Cookie， 以及對頻繁請求觸發驗證碼。OpenCLI 的 Bilibili Adapter 已內建這些處理邏輯， Playwright 版本若未完整實作，輕則資料缺失，重則帳號被封。

18.4 各自的優勢場景

OpenCLI 更適合

  • 快速資料擷取 prototype（分鐘內完成）
  • CI/CD 中的平台操作（發佈、監控、通知）
  • 非技術人員的自動化需求（CLI 友善）
  • 跨平台資料聚合腳本（Twitter + GitHub + HN）
  • AI Agent 工具調用（語義清晰，token 消耗少）
  • 需要定期執行的排程任務
  • Shell Script / Python 的輕量整合

Playwright 更適合

  • E2E 測試（登入流程、表單提交、視覺回歸）
  • 尚無 Adapter 的私有 / 內部系統
  • 需要精確控制每一步互動的場景
  • 複雜 SPA 動態行為（Vue / React / Angular 應用）
  • 截圖 / PDF 產生（page.screenshot()）
  • 網路請求攔截與 Mock（測試環境）
  • 需要多標籤頁協作的複雜流程

18.5 搭配使用策略

OpenCLI 與 Playwright 並非競爭關係，而是互補的工具組合。 最佳實踐是：有 Adapter 的平台用 OpenCLI，其餘場景用 Playwright， 必要時在 Custom Adapter 內部呼叫 Playwright 作為底層引擎。

在 Custom Adapter 中整合 Playwright

當你需要為複雜的私有系統建立 Custom Adapter，又需要精細控制互動流程時， 可以在 Adapter 的 TypeScript 實作裡直接使用 Playwright：

internal-erp/index.ts — Adapter 內整合 Playwright 
import { defineAdapter } from '@opencli/adapter-sdk';
import { chromium, Browser, BrowserContext } from 'playwright';

let browser: Browser | null = null;
let context: BrowserContext | null = null;

export default defineAdapter({
  name: 'internal-erp',
  version: '1.0.0',
  description: '內部 ERP 系統 Adapter（使用 Playwright 底層）',
  baseUrl: 'https://erp.internal.company.com',

  // Adapter 初始化：啟動 Playwright
  async setup() {
    browser = await chromium.launch({ headless: true });
    context = await browser.newContext({
      storageState: process.env.ERP_SESSION_PATH
    });
  },

  // Adapter 清理：關閉瀏覽器
  async teardown() {
    await context?.close();
    await browser?.close();
  },

  commands: {
    'get-inventory': {
      description: '取得庫存清單（複雜 SPA，需要 Playwright 精確控制）',
      args: {
        category: { type: 'string', required: true },
        warehouse: { type: 'string', default: 'all' }
      },
      async execute({ args }) {
        if (!context) throw new Error('Playwright context not initialized');
        const page = await context.newPage();

        try {
          await page.goto(`/inventory?cat=${args.category}`);
          // 等待 Vue/React 元件掛載完成
          await page.waitForFunction(() =>
            document.querySelector('[data-loaded="true"]') !== null
          );

          // 使用 Playwright 填寫篩選表單
          if (args.warehouse !== 'all') {
            await page.selectOption('#warehouse-filter', args.warehouse);
            await page.waitForResponse(res => res.url().includes('/api/inventory'));
          }

          // 擷取表格資料
          const data = await page.$$eval('table.inventory tbody tr', rows =>
            rows.map(row => {
              const cells = Array.from(row.querySelectorAll('td'));
              return {
                sku: cells[0]?.textContent?.trim(),
                name: cells[1]?.textContent?.trim(),
                quantity: parseInt(cells[2]?.textContent ?? '0'),
                location: cells[3]?.textContent?.trim()
              };
            })
          );

          return data;
        } finally {
          await page.close();
        }
      }
    }
  }
});
💡
這個模式的優勢

封裝完成後，使用者只需執行 opencli internal-erp get-inventory --category electronics， 不需要了解任何 Playwright 細節。AI Agent 也能透過語義指令調用這個複雜操作。

混合 Pipeline：OpenCLI 搜尋 + Playwright 深度爬取

對於需要兩階段處理的任務，可以用 OpenCLI 快速取得入口資料， 再用 Playwright 針對每個目標執行深度操作：

hybrid-pipeline.sh 
#!/usr/bin/env bash
# hybrid-pipeline.sh
# 用 OpenCLI 搜尋 GitHub → Playwright 深度爬取每個 Repo 的詳細 Contributors

set -euo pipefail

# Step 1：用 OpenCLI 快速取得熱門 Repo 清單（語義明確、1 行）
REPOS=$(opencli github trending --language rust --since monthly --limit 10 --json)

# Step 2：擷取 Repo slug 列表
SLUGS=$(echo "$REPOS" | jq -r '.[].full_name')

# Step 3：對每個 Repo 用 Playwright 深度爬取 Contributors 頁（OpenCLI 無此指令）
echo "$SLUGS" | while read -r slug; do
  npx ts-node scrape-contributors.ts "$slug" >> contributors.jsonl
  echo "Done: $slug"
done

echo "Pipeline complete. Results in contributors.jsonl"

18.6 效能與資源比較

指標 OpenCLI Playwright 說明
冷啟動時間 ~50–200 ms ~1–3 秒 Playwright 需要啟動完整 Chromium 程序
記憶體佔用 ~30–80 MB ~150–400 MB Chromium 本身記憶體消耗較大
並行能力 Shell 層級 xargs -P Playwright BrowserContext 並行 Playwright 並行更細緻，可共用一個 Browser
CI 環境友善度 高（輕量，無需額外依賴） 中（需安裝 Chromium 瀏覽器依賴） OpenCLI 連線至 Adapter 管理的 browser
適合的批量規模 小到中批量（1–1,000 筆） 中到大批量（1,000+ 筆） 大規模爬取建議 Playwright + 分散式架構
連線重用 自動重用持久 Session 需手動管理 Context 生命週期 OpenCLI browser 模式保持連線，指令間快速切換
ℹ️
關於冷啟動的補充

OpenCLI 的低啟動時間來自「持久瀏覽器 Session」設計： opencli browser start 啟動後，後續每個指令都附著到同一個 browser 程序， 省去反覆啟動 Chromium 的開銷。Playwright 若採用相同的 persistent context 模式， 啟動成本也可以大幅降低。

18.7 從 Playwright 遷移到 OpenCLI

識別可遷移的腳本

遷移的第一步是盤點現有 Playwright 腳本，找出哪些操作的平台已有 OpenCLI Adapter：

查詢可用的 Adapter 列表 
# 列出所有內建 Adapter
opencli adapters list

# 檢查特定平台是否有 Adapter
opencli adapters list | grep -i twitter
opencli adapters list | grep -i github
opencli adapters list | grep -i youtube

遷移優先順序

優先順序 類型 行動
第一優先 有現成 Adapter 的公開平台 直接替換成 OpenCLI 指令
第二優先 操作邏輯單純的內部系統 撰寫 Custom Adapter，再用 OpenCLI
第三優先 資料擷取部分（非測試邏輯） 用 OpenCLI 替換擷取，保留 Playwright 驗證
保留 Playwright E2E 測試套件、視覺回歸、截圖 不遷移，這是 Playwright 的強項

遷移前後程式碼對比

遷移前：純 Playwright 腳本 
// 遷移前：純 Playwright 腳本（每日監控 GitHub 星數）
import { chromium } from 'playwright';

async function checkStars(repos: string[]) {
  const browser = await chromium.launch({ headless: true });
  const results = [];

  for (const repo of repos) {
    const page = await browser.newPage();
    await page.goto(`https://github.com/${repo}`);
    await page.waitForSelector('#repo-stars-counter-star');
    const stars = await page.$eval(
      '#repo-stars-counter-star',
      el => el.textContent?.trim()
    );
    results.push({ repo, stars });
    await page.close();
  }

  await browser.close();
  return results;
}
遷移後：改用 OpenCLI（程式碼量減少 ~80%） 
// 遷移後：改用 OpenCLI（程式碼量減少 ~80%）
import { execSync } from 'child_process';

function checkStars(repos: string[]) {
  return repos.map(repo => {
    const result = execSync(
      `opencli github repo ${repo} --fields stars --json`,
      { encoding: 'utf-8' }
    );
    const data = JSON.parse(result);
    return { repo, stars: data.stargazers_count };
  });
}
💡
漸進式遷移建議

不需要一次全部遷移。建議先在新腳本中使用 OpenCLI，舊腳本維持原樣繼續運作。 等到 OpenCLI 版本穩定且確認產出一致後，再逐步退役 Playwright 版本。

18.8 決策流程圖

面對新的自動化需求時，用以下決策樹快速判斷該使用哪個工具：

工具選擇決策樹 
需要自動化瀏覽器操作？
│
├─ 是已知平台（Twitter / GitHub / YouTube / Bilibili / HN 等）？
│  ├─ 是 → opencli <platform> <command>  ✅ OpenCLI 首選
│  └─ 否 → 繼續往下判斷
│
├─ 是 E2E 測試 / UI 驗證（表單提交、登入流程、視覺回歸）？
│  └─ 是 → Playwright + 測試框架（Vitest / Jest）  ✅
│
├─ 需要 AI Agent / LLM Tool Use 調用？
│  └─ 是 → 優先 OpenCLI（語義指令，token 消耗少）  ✅
│
├─ 是尚無 Adapter 的私有 / 內部系統？
│  ├─ 操作邏輯複雜 → Playwright  ✅
│  └─ 操作邏輯單純 → 先寫 Custom Adapter，再用 OpenCLI  ✅
│
├─ 需要截圖 / PDF 產生？
│  └─ 是 → Playwright（page.screenshot / page.pdf）  ✅
│
└─ 大規模爬取（百頁以上）？
   ├─ 有 Adapter → OpenCLI + shell loop / xargs 並行  ✅
   └─ 無 Adapter → Playwright parallel contexts  ✅

如果還是拿不定主意，有一個簡單的經驗法則： 先嘗試用 opencli adapters list 查找對應的 Adapter； 找到了就用 OpenCLI，找不到再考慮 Playwright 或撰寫 Custom Adapter。

18.9 本章小結

OpenCLI 與 Playwright 解決的是同一個底層問題（瀏覽器自動化），但在不同的抽象層次上工作：

  • OpenCLI 封裝了平台知識，適合「我要資料」的語義需求，是 AI Agent 和快速自動化的首選。
  • Playwright 提供底層控制，適合「我要精確操作」的測試與自訂場景。
  • 兩者可以在 Custom Adapter 的架構下結合使用——Playwright 作為引擎，OpenCLI 作為語義介面。
  • 遷移策略：有 Adapter 的平台優先換用 OpenCLI，E2E 測試套件保留 Playwright。
