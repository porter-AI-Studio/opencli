第 6 章 · Part 2：瀏覽器自動化

元素定位策略

告訴 OpenCLI「要操作哪個元素」，是自動化的核心挑戰。本章系統介紹三種定位方式——N 索引、CSS Selector、find 指令——並說明各自的適用場景、穩定性差異，以及如何在動態頁面中找到最可靠的定位方案。

6.1 三種定位方式概覽

OpenCLI 提供三種方式來指定目標元素，從最快速的互動探索到最穩定的自動化腳本，各有其最佳使用時機：

方式語法範例適用場景自動化穩定性
N 索引 click 3 互動式探索、快速測試 ❌ 不穩定
CSS Selector click "#submit-btn" 自動化腳本、CI 測試 ✅ 穩定（取決於 selector 品質）
find 指令 find --text "送出" 動態內容、沒有好 selector 時 ⚠️ 視頁面而定

6.2 N 索引：互動式探索利器

執行 state 指令後，OpenCLI 會列出頁面所有可互動元素，並在每個元素前標上 [N] 編號。你可以直接把這個數字傳給 click、fill 等指令，無需輸入任何 selector。

先用 state 查看頁面元素 
opencli browser work state

# 典型輸出示例：
# Interactive elements:
# [1] a "首頁" href="/"
# [2] a "關於我們" href="/about"
# [3] input[type="search"] #search placeholder="搜尋..."
# [4] button "搜尋" .search-btn
# [5] textarea #message-input placeholder="輸入訊息"
# [6] button "送出" .submit-btn[disabled]
用 N 索引直接操作 
# 點擊第 4 個元素（搜尋按鈕）
opencli browser work click 4

# 在第 3 個元素（搜尋框）輸入文字
opencli browser work fill 3 "OpenCLI 教學"

# 點擊第 6 個元素（送出按鈕）
opencli browser work click 6

N 索引的優點是零學習成本——打開 state 看一眼就能操作。在終端機裡快速探索一個陌生頁面時非常好用。

🚫
N 索引不能用於自動化腳本

N 索引在頁面任何內容變化後都會重新編號。頁面 AJAX 更新、新增一則通知、展開一個選單，都可能讓 [3] 變成別的元素。將 N 索引寫進自動化腳本，等於埋下難以追蹤的定時炸彈——腳本可能在某天毫無預警地點錯地方。請改用 CSS Selector。

❌ 錯誤用法：在自動化腳本中使用 N 索引 
# ❌ 不要這樣做——頁面一有變化就會壞掉
opencli browser work click 3
opencli browser work fill 5 "porter@example.com"
opencli browser work click 7

6.3 state 指令深入說明

state 不只是列出 N 索引，它同時提供了選擇 CSS Selector 的重要線索。每行輸出包含：

  • [N] — N 索引編號
  • 元素標籤（input、button、a、textarea 等）
  • 顯示文字（如有，以引號包圍）
  • CSS selector 提示（#id、.class）
  • 特殊屬性（href、placeholder、disabled 等）
state 輸出範例解讀 
opencli browser work state

# [1] a "首頁" href="/"
#  └─ 可用：click "a[href='/']"  或  click 1（互動探索）
#
# [3] input[type="search"] #search placeholder="搜尋..."
#  └─ 可用：fill "#search" "關鍵字"
#
# [6] button "送出" .submit-btn[disabled]
#  └─ 元素目前 disabled，click 會被忽略或報錯，需先確認狀態
💡
從 state 輸出挑 selector 的技巧

優先選 #id 形式的 selector（最穩定）。若沒有 id，看有沒有語意化的 class 名稱（避開 .css-1a2b3c 這類 CSS-in-JS 生成的亂碼 class）。也可以注意 placeholder、name、type 等屬性，用屬性 selector 定位。

6.4 CSS Selector：自動化首選

CSS Selector 是 OpenCLI 自動化腳本的標準定位方式。只要頁面結構沒有大幅重構，selector 就能穩定工作。

基礎 Selector 類型

ID、Class、屬性 Selector 
# ID selector（最穩定，頁面內唯一）
opencli browser work click "#submit-btn"
opencli browser work fill "#username" "porter"

# Class selector
opencli browser work click ".btn-primary"

# 屬性 selector（name、type、data-* 屬性）
opencli browser work fill "[name='username']" "porter"
opencli browser work fill "[name='password']" "secret"
opencli browser work click "[type='submit']"

# data-testid（測試專用屬性，最推薦）
opencli browser work fill "[data-testid='username-input']" "porter"
opencli browser work click "[data-testid='login-button']"

# aria 屬性（語意化，不依賴視覺樣式）
opencli browser work click "[aria-label='關閉對話框']"
opencli browser work click "[role='button'][aria-label='送出']"

組合與結構性 Selector

組合 Selector 精確定位 
# 限定在特定容器內
opencli browser work click "form.login-form button[type='submit']"
opencli browser work fill ".chat-panel textarea.chat-input" "你好"

# 最後一個子元素
opencli browser work click ".message-list .message:last-child"

# 第 N 個元素
opencli browser work click ".tab-item:nth-child(2)"

# 直接子元素（避免找到嵌套子孫）
opencli browser work click ".nav > a.active"
雙引號 vs 單引號
CSS Selector 本身含有單引號時（如 [name='email']），外層請用雙引號包裹整個 selector 字串。在 shell 腳本中，可用跳脫字元或調整引號層次避免衝突。

6.5 find 指令：彈性查詢

當頁面沒有好的 CSS selector，或你想用文字描述元素時，find 指令提供更彈性的查詢方式。find 回傳元素的 ref 資訊，也可直接用於定位。

find 語法

find 指令完整語法 
opencli browser <session> find [--text <文字>] [--selector <css>]

# 用顯示文字找元素
opencli browser work find --text "新增"
opencli browser work find --text "Submit"
opencli browser work find --text "確認刪除"

# 用 CSS selector 找（回傳詳細資訊）
opencli browser work find --selector "textarea.chat-input"
opencli browser work find --selector "#login-form input[name=email]"

# 在特定容器內用文字找
opencli browser work find --selector ".sidebar a" --text "設定"

find 輸出格式

find 成功後回傳 JSON 格式的元素資訊，包含 ref 編號、標籤、文字內容與 selector：

find 回傳範例 
# 執行
opencli browser work find --text "送出"

# 輸出
# {
#   "ref": 5,
#   "tag": "button",
#   "text": "送出",
#   "selector": ".submit-btn",
#   "visible": true
# }
💡
find 的 --text 是部分比對

--text "送出" 會比對包含「送出」文字的所有可見元素。若頁面有多個符合的元素，find 回傳第一個。需要更精確時，搭配 --selector 縮小範圍。

6.6 定位策略選擇原則

面對不同情境，有不同的最佳定位策略。以下表格彙整常見情境的建議做法：

情境建議方式範例
互動式探索頁面 N 索引（配合 state） state → click 4
自動化腳本、CI 測試 CSS Selector click "#login-btn"
前端有設 data-testid [data-testid="..."]（最優先） click "[data-testid='submit']"
表單元素有 name 屬性 [name="..."] fill "[name='email']" "test@example.com"
沒有好的 CSS selector find --text "..." find --text "確認"
動態生成的元素 wait 後再用 CSS Selector wait selector ".result" → click ".result .action"
CSS-in-JS 框架（亂碼 class） aria 屬性或 eval click "[aria-label='送出']"

6.7 穩定 vs 脆弱的 Selector

selector 的品質直接決定自動化腳本的壽命。以下對比常見的好壞範例：

容易壞的 Selector

❌ 脆弱 Selector 範例 
# ❌ CSS-in-JS 動態生成的亂碼 class（每次 build 都不一樣）
opencli browser work click ".css-1a2b3c4"
opencli browser work click ".sc-bdnxRM"

# ❌ N 索引（頁面任何變化都會重新編號）
opencli browser work click 7
opencli browser work fill 3 "porter@example.com"

# ❌ 過度依賴 DOM 層級結構（重構就壞）
opencli browser work click "div > div > div:nth-child(3) > span > button"

# ❌ 用 inline style 定位（樣式改了就找不到）
opencli browser work click "[style='color: red; font-weight: bold']"

穩定的 Selector

✅ 穩定 Selector 範例 
# ✅ ID（最穩定，頁面內唯一）
opencli browser work click "#login-btn"
opencli browser work fill "#email-input" "porter@example.com"

# ✅ data-testid（測試專用屬性，不受樣式重構影響）
opencli browser work fill "[data-testid='username']" "porter"
opencli browser work click "[data-testid='submit-button']"

# ✅ aria-label（語意化，不依賴視覺實作）
opencli browser work click "[aria-label='關閉對話框']"
opencli browser work click "[aria-label='下一頁']"

# ✅ name 屬性（表單元素幾乎不會改）
opencli browser work fill "[name='email']" "test@example.com"
opencli browser work fill "[name='password']" "secret"

# ✅ 語意化結構（不太會變，且意圖明確）
opencli browser work click "nav .main-menu a[href='/dashboard']"
opencli browser work click "header button[type='submit']"
💡
說服前端工程師加 data-testid

若你維護的專案有前端代碼控制權，在關鍵元素加上 data-testid 屬性是最低成本、最高回報的自動化投資。這個屬性對使用者不可見、不影響樣式，卻能讓測試腳本完全不受 UI 重構影響。

6.8 處理動態元素

現代 SPA 頁面大量使用 AJAX 和動態渲染，元素可能在操作後才出現或消失。直接定位尚未出現的元素會得到 selector_not_found 錯誤。正確做法是先等待再定位。

等待元素出現後再操作 
# 等待 API 回應後出現的結果列表
opencli browser work wait selector ".search-results" --timeout 10000

# 等出現後再操作列表內的元素
opencli browser work click ".search-results .result-item:first-child a"

# 等待聊天機器人回覆出現
opencli browser work wait selector ".message.bot-message:last-child" --timeout 30000

# 等待後取得最新回覆的內容
opencli browser work eval "document.querySelector('.message.bot-message:last-child .content').textContent"
等待元素消失（確認操作完成） 
# 點擊刪除後，等待確認對話框出現
opencli browser work click "[data-testid='delete-btn']"
opencli browser work wait selector ".confirm-dialog" --timeout 5000

# 確認刪除
opencli browser work click "[data-testid='confirm-delete']"

# 等待對話框消失，確認操作完成
# （若對話框關閉後頁面重整，直接 wait selector 新頁面的元素）
opencli browser work wait selector ".success-toast" --timeout 5000
⚠️
避免使用固定 wait time

不要用 wait time 3 來「等頁面載入」。固定等待在快速環境下浪費時間，在慢速環境下又不夠用。請改用 wait selector 或 wait text 等事件驅動的等待策略，腳本才能在各種環境下穩定運行。

6.9 在 Vitest 測試中使用 Selector

將 OpenCLI 整合進 Vitest 測試時，selector 策略的品質尤為關鍵。以下示範標準的包裝與使用模式：

helpers/opencli.ts — 包裝 OpenCLI 指令 
// helpers/opencli.ts
import { execa } from 'execa';

export async function browser(...args: string[]) {
  const result = await execa('opencli', ['browser', 'work', ...args]);
  return JSON.parse(result.stdout);
}

export async function click(selector: string) {
  return browser('click', selector);
}

export async function fill(selector: string, value: string) {
  return browser('fill', selector, value);
}

export async function waitFor(selector: string, timeout = 10000) {
  return browser('wait', 'selector', selector, '--timeout', String(timeout));
}
spec 中使用穩定 Selector 
// tests/chat.spec.ts
import { click, fill, waitFor, browser } from './helpers/opencli';

test('送出訊息並收到回覆', async () => {
  // 使用 data-testid（最穩定）
  await fill('[data-testid="message-input"]', '你好，請介紹一下自己');
  await click('[data-testid="send-button"]');

  // 等待 bot 回覆出現
  await waitFor('.message.bot-message', 30000);

  // 取得最新回覆文字
  const text = await browser('eval',
    "document.querySelector('.message.bot-message:last-child .content').textContent"
  );

  expect(text.length).toBeGreaterThan(10);
});

6.10 eval：終極定位手段

當頁面結構極為特殊、CSS selector 難以精確命中，或需要複雜的條件定位時，eval 讓你用完整的 JavaScript 邏輯找到元素。

eval 定位與操作範例 
# 找特定文字的元素然後點擊
opencli browser work eval "document.querySelector('.messages .message:last-child .copy-btn').click()"

# 計算頁面上 bot 訊息的數量（用於等待或斷言）
opencli browser work eval "document.querySelectorAll('.message.bot').length"

# 找所有包含特定文字的按鈕，點擊第一個
opencli browser work eval "
  Array.from(document.querySelectorAll('button'))
    .find(btn => btn.textContent.trim() === '複製')
    ?.click()
"

# 讀取特定位置的表格儲存格值
opencli browser work eval "document.querySelector('table tbody tr:nth-child(2) td:nth-child(3)').textContent.trim()"
⚠️
eval 是最後手段，不是首選

雖然 eval 威力強大，但它繞過了 OpenCLI 的事件模擬機制，直接執行 JS 的 .click() 不一定會觸發框架的事件處理器（React、Vue 的合成事件系統）。能用 CSS Selector 解決的，優先用 CSS Selector；需要等待的，先用 wait 再定位；只有真的找不到合適 selector 時，才動用 eval。

6.11 定位方式快速決策流程

面對一個要操作的元素，依以下順序評估：

  1. 有 data-testid 嗎？ → 直接用 [data-testid="..."]，最優先
  2. 有唯一的 id 嗎？ → 用 #id-name
  3. 是表單元素且有 name 嗎？ → 用 [name="field-name"]
  4. 有語意化的 aria-label 嗎？ → 用 [aria-label="..."]
  5. 有穩定的語意 class（非 CSS-in-JS）嗎？ → 組合結構 selector
  6. 以上都不適合？ → 用 find --text "..." 或 eval
  7. 只是快速探索？ → 用 state + N 索引，但不寫進腳本
小結：定位是可維護性的基礎
好的 selector 策略讓腳本在頁面改版後繼續工作；壞的 selector 讓你在每次 UI 調整後都要重寫測試。從一開始就選對定位方式，是讓自動化投資長期有效的關鍵。
