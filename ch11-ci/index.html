第 11 章：CI/CD 整合

將 OpenCLI 整合進 CI/CD pipeline 是讓瀏覽器自動化真正發揮價值的關鍵一步。無論是定期的資料擷取、端到端測試、還是部署後的冒煙測試（smoke test），OpenCLI 都能在持續整合環境中穩定運行。

本章涵蓋三大主流 CI/CD 平台的完整配置方案，並說明各平台之間的關鍵差異，讓你能快速上手而不踩坑。

CI 環境的核心限制：必須使用 CDP 模式

在本地開發時，OpenCLI 預設透過 Chrome Extension 與瀏覽器溝通。但 CI 環境無法安裝 Extension（沒有使用者介面、無法與 Chrome Web Store 互動），因此 CI 環境必須改用 CDP 模式（Chrome DevTools Protocol）。

CDP 模式的運作方式是：先啟動一個支援遠端除錯的 Chrome 或相容瀏覽器服務，再透過 WebSocket 連線讓 OpenCLI 發送指令。這種方式完全不依賴 Extension，因此可以在任何無頭環境中執行。

關鍵環境變數

在 CI 環境中，你需要透過環境變數告訴 OpenCLI 如何連線到瀏覽器。以下是完整的環境變數清單：

環境變數 說明 預設值
OPENCLI_CDP_ENDPOINT CDP 連線端點，支援 http:// 與 ws:// 兩種格式 http://localhost:9222
OPENCLI_CDP_TARGET 多個 target 時，以 URL substring 過濾要連線的 target （不過濾）
OPENCLI_DAEMON_PORT OpenCLI daemon 監聽的本地埠號 19825
OPENCLI_BROWSER_CONNECT_TIMEOUT 等待瀏覽器連線就緒的最長秒數 30
OPENCLI_BROWSER_COMMAND_TIMEOUT 單一指令執行的最長秒數，超過則視為失敗 60
OPENCLI_VERBOSE 設為 1 或 true 時，輸出詳細的除錯 log false

三種瀏覽器方案

在 CI 環境中啟動可供 OpenCLI 連線的瀏覽器，有三種主要方案，各有適用情境：

方案 A：browserless/chromium（推薦）

browserless 是專為無頭瀏覽器自動化設計的 Docker 映像，提供完整的 Chrome 環境並內建健康檢查、並行連線管理、Token 認證等功能。這是最推薦的方案，穩定性最高且設定最簡潔。 

# GitHub Actions 完整配置範例

name: OpenCLI Automation

on:
  push:
    branches: [main]
  schedule:
    - cron: '0 9 * * 1-5'  # 週一到週五早上 9 點執行

jobs:
  scrape:
    runs-on: ubuntu-latest

    services:
      browserless:
        image: ghcr.io/browserless/chromium
        ports:
          - 3000:3000
        env:
          CONCURRENT: 5
          TOKEN: ${{ secrets.BROWSERLESS_TOKEN }}
        options: >-
          --health-cmd "curl -f http://localhost:3000/json/version"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Install OpenCLI
        run: npm install -g @jackwener/opencli

      - name: Verify connection
        env:
          OPENCLI_CDP_ENDPOINT: "ws://localhost:3000?token=${{ secrets.BROWSERLESS_TOKEN }}"
        run: opencli doctor

      - name: Run automation
        env:
          OPENCLI_CDP_ENDPOINT: "ws://localhost:3000?token=${{ secrets.BROWSERLESS_TOKEN }}"
          OPENCLI_BROWSER_CONNECT_TIMEOUT: 60
          OPENCLI_BROWSER_COMMAND_TIMEOUT: 120
        run: |
          opencli <adapter> <command> --format json > output.json
          echo "Automation completed, $(wc -l < output.json) records found"

      - name: Upload results
        uses: actions/upload-artifact@v4
        with:
          name: opencli-results
          path: output.json
          retention-days: 30

為什麼推薦 browserless？

  • 內建 CONCURRENT 控制並行連線數，避免資源耗盡
  • Token 認證防止未授權存取
  • GitHub Actions 原生支援 --health-cmd，自動等待服務就緒再執行後續 step
  • 映像已包含所有必要的系統依賴，不需要另外安裝字型或 sandbox 相關套件

方案 B：原生 Chrome Headless

如果不想依賴額外的 Docker service，可以直接在 CI runner 上啟動 Chrome。GitHub Actions 的 ubuntu-latest 已預裝 Google Chrome，可直接使用。 

steps:
  - name: Start Chrome in headless mode
    run: |
      google-chrome \
        --headless=new \
        --no-sandbox \
        --disable-dev-shm-usage \
        --remote-debugging-port=9222 \
        --remote-allow-origins="*" \
        --user-data-dir=/tmp/chrome-profile \
        &

      # 等待 Chrome 啟動完成
      echo "Waiting for Chrome to start..."
      for i in $(seq 1 10); do
        if curl -sf http://localhost:9222/json/version > /dev/null; then
          echo "Chrome is ready"
          break
        fi
        sleep 1
      done

  - name: Install OpenCLI
    run: npm install -g @jackwener/opencli

  - name: Run automation
    env:
      OPENCLI_CDP_ENDPOINT: "http://localhost:9222"
      OPENCLI_VERBOSE: "1"
    run: opencli <adapter> <command> --format json > output.json

注意：直接啟動 Chrome 的限制

  • 需要手動處理 Chrome 的啟動時序（固定 sleep 3 不可靠，建議用 polling curl）
  • 不支援並行連線，若需同時執行多個 task 需要啟動多個 Chrome 實例
  • CI runner 重啟後，背景 Chrome 程序不會自動清理

方案 C：Selenium Grid（並行多瀏覽器）

當你需要跨瀏覽器測試或高度並行的任務時，Selenium Grid 提供集中管理多個瀏覽器節點的能力。 

services:
  selenium-hub:
    image: selenium/hub:4.18
    ports:
      - 4444:4444
      - 4442:4442
      - 4443:4443

  chrome-node:
    image: selenium/node-chrome:4.18
    environment:
      SE_EVENT_BUS_HOST: selenium-hub
      SE_EVENT_BUS_PUBLISH_PORT: 4442
      SE_EVENT_BUS_SUBSCRIBE_PORT: 4443
      SE_NODE_MAX_SESSIONS: 3
    options: --shm-size="2g"
    depends_on:
      - selenium-hub

steps:
  - name: Wait for Grid to be ready
    run: |
      until curl -sf http://localhost:4444/wd/hub/status | grep -q '"ready":true'; do
        echo "Waiting for Selenium Grid..."
        sleep 2
      done

  - name: Run OpenCLI via Grid
    env:
      OPENCLI_CDP_ENDPOINT: "http://localhost:4444"
    run: opencli <adapter> <command>

Docker Compose 本地開發環境

為確保本地開發與 CI 環境一致，建議在專案中加入 docker-compose.yml，讓開發者在本地也能用相同的瀏覽器環境測試： 

# docker-compose.yml（放在專案根目錄）

version: '3.8'

services:
  browserless:
    image: ghcr.io/browserless/chromium
    ports:
      - "3000:3000"
    environment:
      CONCURRENT: 5
      TOKEN: devtoken
    shm_size: '2gb'
    restart: unless-stopped

# 使用方式：
# docker compose up -d
# OPENCLI_CDP_ENDPOINT="ws://localhost:3000?token=devtoken" opencli doctor
# 本地開發時的快速啟動腳本（scripts/dev-browser.sh）

#!/bin/bash
set -e

echo "Starting browserless..."
docker compose up -d browserless

echo "Waiting for browserless to be ready..."
until curl -sf http://localhost:3000/json/version > /dev/null; do
  sleep 1
done

echo "Browserless is ready!"
echo ""
echo "Set this environment variable to use OpenCLI:"
echo "  export OPENCLI_CDP_ENDPOINT='ws://localhost:3000?token=devtoken'"
echo ""
echo "Or run directly:"
echo "  OPENCLI_CDP_ENDPOINT='ws://localhost:3000?token=devtoken' opencli doctor"

GitLab CI 配置

GitLab CI 的 service 運作機制與 GitHub Actions 有一個關鍵差異：service 的 alias 會直接作為 hostname 使用，而不是 localhost。 

# .gitlab-ci.yml

stages:
  - test
  - scrape

variables:
  OPENCLI_CDP_ENDPOINT: "ws://browserless:3000?token=ci-token"
  OPENCLI_BROWSER_CONNECT_TIMEOUT: "60"

.browser_service: &browser_service
  services:
    - name: ghcr.io/browserless/chromium
      alias: browserless
      variables:
        TOKEN: "ci-token"
        CONCURRENT: "5"

opencli_smoke_test:
  <<: *browser_service
  stage: test
  image: node:20
  before_script:
    - npm install -g @jackwener/opencli
    - |
      echo "Waiting for browserless..."
      for i in $(seq 1 30); do
        if curl -sf http://browserless:3000/json/version > /dev/null; then
          echo "Browserless is ready"
          break
        fi
        sleep 2
      done
  script:
    - opencli doctor
    - opencli <adapter> <command> --format json > output.json
  artifacts:
    paths:
      - output.json
    expire_in: 1 week
  only:
    - main
    - merge_requests

GitLab CI 關鍵差異：Hostname 不是 localhost

在 GitHub Actions 中，service 對應到 localhost。但在 GitLab CI 中，service 對應到其 alias 名稱（例如 browserless）。因此環境變數要設為 ws://browserless:3000，而不是 ws://localhost:3000。這是跨平台遷移時最常見的錯誤。

Jenkins Pipeline

Jenkins 沒有原生的 service 概念，需要手動管理 Docker 容器的生命週期。使用 post { always {} } 確保容器在 pipeline 結束後一定會被清理。 

// Jenkinsfile

pipeline {
    agent { label 'linux' }

    environment {
        BROWSERLESS_TOKEN = credentials('browserless-token')
        OPENCLI_CDP_ENDPOINT = "ws://localhost:3000?token=${BROWSERLESS_TOKEN}"
        OPENCLI_BROWSER_CONNECT_TIMEOUT = '60'
        OPENCLI_BROWSER_COMMAND_TIMEOUT = '120'
    }

    stages {
        stage('Start Browser Service') {
            steps {
                script {
                    sh """
                        docker run -d \
                            --name browserless-${BUILD_NUMBER} \
                            -p 3000:3000 \
                            -e TOKEN=${BROWSERLESS_TOKEN} \
                            -e CONCURRENT=5 \
                            --shm-size=2g \
                            ghcr.io/browserless/chromium

                        echo "Waiting for browserless to start..."
                        for i in $(seq 1 30); do
                            if curl -sf http://localhost:3000/json/version > /dev/null; then
                                echo "Browserless is ready"
                                break
                            fi
                            sleep 2
                        done
                    """
                }
            }
        }

        stage('Install OpenCLI') {
            steps {
                sh 'npm install -g @jackwener/opencli'
                sh 'opencli doctor'
            }
        }

        stage('Run Automation') {
            steps {
                sh 'opencli <adapter> <command> --format json > output.json'
                archiveArtifacts artifacts: 'output.json', fingerprint: true
            }
        }
    }

    post {
        always {
            sh """
                docker stop browserless-${BUILD_NUMBER} || true
                docker rm browserless-${BUILD_NUMBER} || true
            """
        }
        failure {
            sh 'OPENCLI_VERBOSE=1 opencli doctor || true'
        }
    }
}

常見問題排查

問題 1：Chrome 啟動太慢導致連線失敗

使用固定的 sleep 3 不可靠，因為 CI runner 的效能會波動。建議改用 polling curl 直到服務回應： 

# 不推薦：固定等待
sleep 3

# 推薦：polling 直到就緒（最多等 30 秒）
for i in $(seq 1 15); do
  if curl -sf http://localhost:9222/json/version > /dev/null 2>&1; then
    echo "Chrome is ready after ${i} attempts"
    break
  fi
  echo "Attempt ${i}: Chrome not ready yet..."
  sleep 2
done

問題 2：/dev/shm 空間不足導致 Chrome 崩潰

Chrome 預設使用 /dev/shm（共享記憶體）作為渲染緩衝區。CI 環境的 /dev/shm 通常只有 64MB，複雜頁面容易溢出而導致 Tab 崩潰。有兩種解法：

# 解法 1：啟動 Chrome 時關閉 /dev/shm 使用（改用 /tmp）
google-chrome --disable-dev-shm-usage ...

# 解法 2：在 Docker Compose 或 CI service 中增加 shm 大小
services:
  browserless:
    image: ghcr.io/browserless/chromium
    shm_size: '2gb'   # 直接在 service 設定

# GitHub Actions service 寫法
options: --shm-size="2g"

問題 3：ERR_CONNECTION_REFUSED（remote debugging 連不上）

啟動 Chrome 時，必須加上 --remote-allow-origins="*"，否則 Chrome 會拒絕來自非 localhost 的 CDP 連線請求： 

google-chrome \
  --headless=new \
  --no-sandbox \
  --disable-dev-shm-usage \
  --remote-debugging-port=9222 \
  --remote-allow-origins="*"   # 這行不能省略！

問題 4：需要登入的網站無法在 CI 執行

對於需要帳密登入的網站，有兩種常見解法。推薦的方法是事先在本地登入並匯出 cookies，再存為 CI Secret： 

# 步驟 1：本地匯出 cookies（登入後執行）
opencli browser eval "JSON.stringify(document.cookie)" > cookies.json

# 步驟 2：加密後存入 CI Secret（GitHub Actions）
# 在 GitHub repo -> Settings -> Secrets -> New secret
# Name: SITE_COOKIES
# Value: 貼上 cookies.json 的內容

# 步驟 3：CI 中使用
steps:
  - name: Restore cookies
    env:
      SITE_COOKIES: ${{ secrets.SITE_COOKIES }}
    run: |
      echo "${SITE_COOKIES}" > cookies.json
      opencli browser eval "
        const cookies = JSON.parse(require('fs').readFileSync('cookies.json', 'utf8'));
        document.cookie = cookies;
      "

問題 5：記憶體不足（Out of Memory）

大量並行的瀏覽器操作可能導致 OOM。有三個調整方向：

# 方向 1：降低 browserless 的並行數
environment:
  CONCURRENT: 2   # 從 5 降到 2

# 方向 2：換用更大規格的 runner（GitHub Actions）
runs-on: ubuntu-latest-8core   # 8 核心 32GB 記憶體

# 方向 3：為 Chrome 設定記憶體上限
google-chrome --js-flags="--max-old-space-size=512"

進階：並行執行與 Matrix 策略

當需要對多個目標並行執行時，可以結合 CI 的 matrix 功能與 browserless 的並行連線： 

# GitHub Actions Matrix 並行範例

jobs:
  scrape:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        target: [site-a, site-b, site-c]
      max-parallel: 3   # 同時最多跑 3 個 job

    services:
      browserless:
        image: ghcr.io/browserless/chromium
        ports:
          - 3000:3000
        env:
          CONCURRENT: 5
          TOKEN: ${{ secrets.BROWSERLESS_TOKEN }}
        options: >-
          --health-cmd "curl -f http://localhost:3000/json/version"
          --health-interval 10s
          --health-retries 5

    steps:
      - name: Install OpenCLI
        run: npm install -g @jackwener/opencli

      - name: Run for ${{ matrix.target }}
        env:
          OPENCLI_CDP_ENDPOINT: "ws://localhost:3000?token=${{ secrets.BROWSERLESS_TOKEN }}"
        run: |
          opencli <adapter> <command> \
            --target ${{ matrix.target }} \
            --format json > result-${{ matrix.target }}.json

      - name: Upload result
        uses: actions/upload-artifact@v4
        with:
          name: result-${{ matrix.target }}
          path: result-${{ matrix.target }}.json

安全最佳實踐

  • ✓
    永遠為 browserless 設定 Token：即使在私有 CI 環境，也應啟用 Token 認證，防止 runner 上其他 job 誤用瀏覽器資源。
  • ✓
    不要在 log 中印出 Secret：設定 OPENCLI_VERBOSE=1 時，CDP endpoint URL 可能包含 Token，確認 CI 有遮罩敏感字串的機制。
  • ✓
    限制 Artifact 保存時間：擷取的資料可能包含敏感內容，設定合理的 retention-days（例如 7-30 天）。
  • ✓
    使用最小權限原則：CI job 只需要讀取特定 Secret，不要把所有 Secret 都注入到每個 job。

小結

將 OpenCLI 整合進 CI/CD pipeline 的核心要點：

  1. CI 環境必須使用 CDP 模式，不支援 Extension 模式
  2. 推薦使用 browserless/chromium Docker 映像，穩定且易於配置
  3. GitLab CI 的 service hostname 是 alias 名稱，不是 localhost，這是跨平台遷移最容易搞混的地方
  4. 健康檢查很重要，不要用固定 sleep，要用 polling curl 等待服務就緒
  5. /dev/shm 不足是 Chrome 崩潰的常見原因，加上 --disable-dev-shm-usage 或增大 shm_size
